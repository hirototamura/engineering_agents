# スクラバーの評価

このシナリオはモック ECLSS/EPS ステーションの決定論的な健全性と復旧指標を記録します。SSOS のスコア、キューブの制約検査、プロジェクト共通の得点は使いません。既存出力の読み方は[利用者向け結果ガイド](../../../users/scenarios/scrubber_degradation/results.md)を参照してください。

## 正本となる検査

[environment/scrubber/eclss_ops/telemetry.py](https://github.com/hirototamura/engineering_agents/blob/main/src/environment/scrubber/eclss_ops/telemetry.py) が `co2_health()`、`power_health()`、`overall_health()` と共有定数を持ちます。公開する値と等号の扱いの正本は[結果ガイド](../../../users/scenarios/scrubber_degradation/results.md)にあります。

操作・復旧の定数と健全性の帯の定数を区別します。規則制御、復旧時刻、ダッシュボードの基準線は操作しきい値を共用し、総合健全性は資源状態の悪い方を選びます。このモデル固有の検査です。変更では意図した境界の扱いを守り、正本となる利用者向け契約を更新してください。

## 要約の意味

`scenario_run.py` は CO₂ 最大値、電力余裕最小値、最終テレメトリと健全性、異常の有無、CO₂ が復旧しきい値へ最初に達した時刻、その後初めて下回った時刻、最初の適用済み EPS ブースト、電力の危険状態からの回復を記録します。遷移を観測しなかった時刻は空値であり、復旧時間ゼロではありません。

操作前の行と、同一ステップの操作後のアクチュエータ・EPS 更新を保存します。最大値や時刻の集計にはチーム操作前に行う部分があり、最終値は更新後の観測を反映する場合があります。集計変更ではこの差を保ちます。EPS 要求イベントは受理・予約の証拠であり、即時の物理改善の証明ではありません。

## 要約の根拠となる観測を検査する

| 計算 | 出典と時点 | 保持する回帰条件 |
| --- | --- | --- |
| 健全性 | 観測値に対する `telemetry.py` | 境界の等号と悪い資源の採用 |
| 最大・最小 | ステップ観測時のランナー集計 | 操作後の更新を追加区間に数えない |
| CO₂ 復旧 | 最初の到達とその後の復帰 | 到達・復帰がなければ空値 |
| 電力復旧 | 危険の観測後、最初に抜ける時点 | 最初から安全を復旧にしない |
| EPS ブースト時刻 | 種類で絞った適用済み復旧イベント | 拒否要求を供給済み支援にしない |
| 最終状態 | 同一ステップ更新を含む最後の観測 | 要約とアクチュエータ・EPS の記録を一致 |
| 設計提案 | 実行後のチーム出力 | プレビューを変更後の測定にしない |

元の文書の変更前後の図は提案構造の説明に有用です。`apply_dict_change()` のテストが確認するのはプレビュー変換だけです。ループを閉じるテストでは、別の 2 回目の実行で消費した設計と測定応答を確認する必要があります。

## 回帰確認と範囲

`tests/scenario/test_scrubber_baseline.py`、`test_scrubber_with_agents.py` と環境のモック・ステーションのテストを使います。境界の等号、異常なし、回復なし、ブースト拒否、支援終了、最終要約と記録行の一致を確認します。共有定数を変えると規則制御とビューアの基準線にも影響するため、利用箇所を明示的に更新します。

証拠が示すのはモックモデルと実行調整の動作です。実機の生命維持性能ではありません。提案の変更後状態を測定するには、別の実行で適用する必要があります。現行スクラバーは再投入を行いません。
