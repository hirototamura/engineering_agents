# シミュレータのバックエンドを変更する

バックエンド変更では Python のメソッド定義を満たすだけでなく、観測と操作の意味を維持します。対象の[シナリオ実装](../scenarios/index.md)から、単位、時計の進み方、故障フラグ、証拠の要件を確認してください。

## 担当する契約を選ぶ

スクラバーの `SimulatorProtocol` はステップ駆動で、スクラバーのテレメトリを返します。SSOS の `EclssBackend` は貯蔵量を観測し、ARS/OGS/WRS のアクション、貯蔵サービス、サブシステム故障を公開します。モックとプラントは明示的な時間進行も持ちます。キューブの `BalancingCubeAdapter` はコンパイル・実行・フィードバックを調整し、`environment/mujoco` が数値実行を担当します。バックエンド追加のために、これらの分野固有の契約を全分野共通へ広げないでください。

モデルと通信は `environment` に実装し、構築とシナリオ設定は担当ランナーに接続します。CLI は対応するシナリオとバックエンドの組み合わせだけを受け付けます。LLM とペルソナの判断はバックエンドに入れません。

## 時間と証拠を維持する

観測で時間が進むかを明示します。SSOS のステップ 0 は初期状態を観測し、以降は対応バックエンドを進めてから観測します。同じステップの操作後の行は、追加の物理時間を進めずに操作の効果を示します。ROS2 の観測は非同期で、開始時のテレメトリ待機が必要です。欠けた貯蔵量をゼロとみなさないでください。

SSOS の質量は内部で kg、水の体積は L を使い、ROS2 の境界で上流の g を変換します。キューブは固定時間刻み、制御周期、試行条件、停止条件を維持します。CPU/GPU の比較は宣言した区間と許容差の範囲でのみ有効です。

## バックエンド交換の確認表

| 論点 | 変更で答える問い | 保持する証拠 |
| --- | --- | --- |
| 単位 | 外部値をどこで変換するか | 自明でない値を使う境界テスト |
| 時計 | 観測は読む、進める、待つのどれか | 初期・操作前・操作後の時刻 |
| 操作完了 | 成功は受付、予約、完了のどれか | 結果と後の測定状態 |
| 故障処理 | 故障中・稼働中に仕事を処理できないか | 拒否イベントと不変条件 |
| 値の欠落 | 不明とゼロを区別するか | 明示的な欠落・時間切れ |
| 後始末 | 例外後に故障・読取器・プロセスを戻すか | 失敗経路の回帰確認 |
| 候補への利用 | 同じバックエンドを構築するか | 適用入力と評価器の一致 |
| 追加依存 | 検出・CPU 経路で未導入パッケージを避けるか | 不在条件のテスト |

プロトコルの詳細は[スクラバー](../scenarios/scrubber_degradation/implementation.md)、[SSOS](../scenarios/ssos_eclss_loop/implementation.md)、[キューブ](../scenarios/balancing_cube/implementation.md)の担当実装に置きます。出力する証拠が変われば評価器の変更も必要です。同名のテレメトリだからと以前の監査を適用できるとは限りません。

## 回帰確認

単位、決定論的な状態遷移、操作の成功と拒否、故障、実行中・容量の保護、後始末、テレメトリ欠落、操作後の記録状態を確認します。プラント変更では質量収支と不変条件を検査します。ROS2 はアダプタのテスト後に専用環境で実サービスを確認します。MuJoCo はネイティブ、GPU 不在、一致のテストを適切な追加環境で確認します。

検証範囲の変更は両言語で記述します。モックによる代替は実行の調整を確認しますが、物理バックエンドの監査結果を引き継ぎません。証拠の検査を変える場合は[評価変更](change-evaluation.md)へ進んでください。
