# 同梱シナリオを追加する

このガイドはリポジトリ内にエンジニアリング事例を追加する手順です。外部シナリオの読み込みは未実装で、[開発作業](../development/external-scenarios.md)を別に整理しています。

## 事例を定義する

ミッション、要件の権限、世界とモデルの仮定、設計変数、実行中の操作、検証条件、最適化指標、証拠、失敗状態を明示します。シミュレーションの範囲と、実機での妥当性確認が必要な主張を区別します。[同梱の 3 事例](../scenarios/index.md)は異なる境界の例として参照し、1 つの分野のスキーマを必須にしないでください。

## 現行実装へ接続する

1. `src/scenario/<name>/scenario.yaml` と、設定、バックエンド・チームの構築、証拠、完了を担当するランナーを追加します。現行 `Scenario` 抽象クラスは契約が適合する範囲で使います。実際のランナーはジョブから追加の引数も受け取ります。
2. シナリオのレジストリを定義し、`scenario/runner.py::_scenario_registry()` で結合します。ディレクトリ検出だけで変わるのは一覧です。`list_scenarios()`、説明、実行可能な名前を一致させます。
3. 汎用経路にない引数が必要なら `scenario/jobs/executor.py` を変更します。提案の採用、進捗通知、シードの上書き、履歴、再作成を適用するか明確に決めます。SSOS の反復の意味を偶然引き継がないでください。
4. 対応するモード、バックエンド、必須入力に合わせて `tools/cli` の検査と振り分けを更新します。分野固有の設定検査は担当モジュールに置きます。YAML などを追加したらインストール時のパッケージデータ定義も確認します。
5. 決定論的な評価を実装し、空でない `summary.json` を出します。判定の再現に必要な実効入力、適用設計、テレメトリ、来歴を保持します。正常終了を報告する前に、不完全と非適用の意味を定義します。

## 現行境界への接続確認

以前の「ディレクトリを追加するだけ」という手順では不十分です。次をまとめて確認します。

| 接続箇所 | 追加・確認する内容 | 最初の回帰確認 |
| --- | --- | --- |
| `scenario/<name>/scenario.yaml` | 梱包するリソース、説明、担当する検査 | 検出とインストール後の参照 |
| `scenario_run.py` の登録 | 実行オブジェクトと空でない要約 | 一時出力への短い正常実行 |
| `runner.py::_scenario_registry()` | 明示的な結合 | 一覧と実行先の一致 |
| `jobs/executor.py` | 追加引数と失敗処理 | 未対応の引数・採用経路の拒否 |
| `tools/cli` | モード、バックエンド、事前確認、既定値 | CLI とジョブで同じ要求を解決 |
| 評価と成果物 | 範囲と証拠欠落時の扱い | 破損証拠が合格できない |
| 読者向け文書 | 既存の利用者・開発者の親構造 | 両言語から契約へ到達 |

`run()` の定義は境界の一部です。例えば `apply_proposals_path` を受け取って無視するランナーは、提案適用を対応済みとしてはいけません。メソッドの有無だけでなく、変わる動作をテストします。

## 境界を確認する

レジストリと一覧の一致、不正設定の拒否、一時領域での短い正常実行、要約の欠落・破損、不正提案、出力の分離、決定論的評価をテストします。実サービスを使わずにバックエンドとプロバイダの失敗を確認します。分野の不変条件と、要件変更で固定比較の成績を改善できないことも確認してください。

両言語で利用者向けの設定・実行・結果ページと、開発者向けの実装・評価ページを作ります。公開設定は[利用者向けリファレンス](../../users/reference/configuration.md)を参照します。完了条件は、その事例固有の証拠契約を持つ、実行・レビュー可能な事例です。広範な外部シナリオ化を先に完了させる必要はありません。
