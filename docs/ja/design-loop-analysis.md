# 設計ループ解析

`tools.analysis` は Engineering Agents のキャンペーンを**設計空間上の力学系**として扱い、それを特徴づけるための統計・実験・図を提供します。順序変数を特定し、転移点を求め、応答を測り、**そのうえで初めて**制御器（設計エージェント）を評価する、という順序で進めます。

これは実行ごとのダッシュボードでは答えられない問いに答えます。いずれも個々の実行ではなく**アンサンブル**の性質だからです。

- どの設計変数が実際に結果を支配し、その臨界値はどこか
- 設計エージェントの提案は結果を動かせるのか、動かせるとして単位努力あたりどれだけか
- 宣言された予算の内側でミッションは達成可能か
- 貪欲探索が機能する程度に応答曲面は滑らかか

## クイックスタート

```bash
# 実験バッテリを実行（約 340 シミュレーション、4 並列で約 1 分）
python3 -m tools.analysis run

# データセットを解析し、英語・日本語の HTML レポートを生成
python3 -m tools.analysis report
python3 -m tools.analysis report --lang ja   # 日本語のみ

# 上記を順に実行
python3 -m tools.analysis all
```

出力は `src/experiments/analysis/` 以下に置かれます。

| パス | 内容 |
| --- | --- |
| `design_loop_analysis.html` | 英語レポート。外部アセットなしの 1 ファイル |
| `design_loop_analysis.ja.html` | 日本語レポート（同じ数値、本文は翻訳） |
| `design_loop_analysis.findings.json` | 算出したすべての数値。差分確認と回帰検出用 |
| `datasets/*.json` | 実験ブロックごとの、1 実行 1 行のフラットな行 |
| `datasets/chain_dynamics.json` | 直列化したループ軌道（`ChainDynamics`）。生の `chains/` が無いとき `report` はここから次数パラメータを再構築する |
| `<block>/<run_id>/` | 生の実行ディレクトリ（git 管理外・再生成可能） |

`run` は実行ディレクトリ単位でキャッシュするため、中断したキャンペーンは最初からではなく途中から再開します。`report` はシミュレータに触れずに何度でも再実行できます。新規チェックアウトでは git 管理外の `chains/` は不要です。ループの原型・ステップノルム・図は `datasets/chain_dynamics.json` から復元します。

`--iterate` 連鎖は `--apply-proposals` と両立しません。出荷設計以外から連鎖を始めるキャンペーンは、初期定格を `--set plant_sim.ars.capacity_kg_day=…`（および OGS / WRS 相当）で焼き込みます。

主なフラット: `--quick` は各グリッドを 3 点に間引いてスモークテストにし、`--workers N` は並列数、`--steps N` はミッション長、`--no-cache` は再シミュレーションの強制、`--root DIR` はツリー全体の移動です。

## 順序変数

3 つのサイジング変数（`plant_sim.ars.capacity_kg_day`、`plant_sim.ogs.max_o2_kg_day`、`plant_sim.wrs.max_feed_l_per_operation`）は単位が異なり、ベースラインも 1 桁違うため直接比較できません。それぞれを同じ量に対する乗員の 1 日あたり需要で割ると、単位点が物理的に意味を持つ無次元の**カバレッジ比**が得られます。

$$
\rho_{\text{ARS}} = \frac{\text{CO}_2\ \text{除去能力}}{N \cdot \dot m_{\text{CO}_2}}, \qquad
\rho_{\text{OGS}} = \frac{\text{O}_2\ \text{生成能力}}{N \cdot \dot m_{\text{O}_2}}, \qquad
\rho_{\text{WRS}} = \frac{\text{WRS スループット}}{N \cdot (\dot m_{\text{尿}} + \dot m_{\text{凝縮水}})}
$$

`ρ = 1` は定常状態で乗員をまかなえる最小の station です。出荷時の `ssos_eclss_loop` の station は乗員 50 名に対して **ρ_ARS = 0.087**、**ρ_OGS = 0.220** に位置します。それぞれ 11 倍・5 倍のアンダーサイズです。

設計空間の距離は `log ρ` で測ります。サイジングは乗法的だからです。サイジングモデルは容量の**比**に対してアフィンであり、ルールベース設計器は一定の乗法ゲインを適用するため、どこから始めても倍化のコストは同じであるべきです。

```python
from tools.analysis.design_space import coverage_ratios, crew_demand

coverage = coverage_ratios(scenario_config)
coverage.minimum            # 律速となるカバレッジ
coverage.binding_subsystem  # "ars" | "ogs" | "wrs"
```

### アクチュエーション空間

設計器が動かせるのはハードウェアだけではありません。押せる 3 か所はそれぞれ挙動が大きく異なります。

| 部分空間 | 軸の例 | 保存先 | 変えるもの |
| --- | --- | --- | --- |
| `capacity` | `plant_sim.ogs.max_o2_kg_day` | scenario config | 据付済みの定格スループット |
| `action` | `agents.actor.policy.ogs_goal.input_water_mass` | agents config | 既存ハードへ乗員が送るペイロード |
| `policy` | `thresholds.co2_storage_high_kg` | scenario config | 乗員が動き出す判定のバンド境界 |

`actuation_vector()` は 3 つすべてにまたがる対数座標を返し、出荷時構成が原点になります。1 本のベクトルにまとめることで、**「ループが動かなかった」**と**「ループは動いたが無意味な方向だった」**を区別できます。結果のプロット上では両者は同一に見えますが、必要な対処は正反対です。

## 実験ブロック

| ブロック | 変化させるもの | 答える問い |
| --- | --- | --- |
| `seed_replicates` | `--seed` のみ | プラントは確率的か |
| `response_surface` | ARS × OGS 定格（11 × 11） | 相図、臨界性、生存のコスト |
| `one_at_a_time` | 1 軸ずつ、出荷時動作点 | ループが出発する点での可制御性 |
| `one_at_a_time_relieved` | 1 軸ずつ、OGS を 42 kg/day に | O2 が律速でなくなった後の可制御性 |
| `crew_scaling` | 乗員数、station 固定 | 崩壊テストの分母側 |
| `iso_ray` | 全容量を共通係数で倍率変更 | 崩壊テストの分子側 |
| `chains` | `--iterate` の長さ | 実際に回っている閉ループ |

設計の適用は、変更 1 件の `capacity_profile` 提案を書いて `--apply-proposals` に渡すことで行います。これは tool-use 設計器が候補を採用するときと同じ経路です。したがって実験グリッドとエージェント自身の提案は、まったく同じコードを通ります。

!!! note "容量変更はペイロードを伴う"
    容量変更を適用すると `sync_action_payloads` も走り、乗員のリクエストが新しいハードウェアが満たせる量まで引き上げられます。したがって応答曲面の各点は、古い手順で運用される新ハードではなく**適切に運用された** station です。one-at-a-time スイープは意図的に同期しないため、ペイロード軸を単独で切り出せます。

## 不確かさはどこにあるか

ルールベースのアクター・設計器では、パイプライン全体が**決定論的**です。同一構成を 6 通りのシードで再生しても、評価スコアと生存乗員数はビット単位で一致します（スプレッド `0.0`）。ブートストラップすべき反復ノイズは存在しません。

そのため本解析が報告する区間はすべて、**設計点とシナリオ条件をまたいで**取られています。変動が実際に存在するのはそちらだからです。感受率は反復間の分散ではなく応答の**微分**です。確率性が入り込むのは LLM 設計器を使う場合だけで、それには到達可能なプロバイダが必要です。

## 出荷時構成で測定された結果

以下は `plant_sim` バックエンド、`labeled_rule_base` のアクターおよび設計器、72 ステップ、乗員 50 名での 341 シミュレーションの結果です。

### 保存則は成立している

物理ゲートは監査対象の状態とは独立に各質量収支を再計算し、341 実行すべてで通過しました。最悪残差は水収支の `1e-12` L（許容 `2e-6`）で、O2 と CO2 の収支は厳密にゼロです。

### ミッションは自らの予算の下で実現不能

グリッド上の 121 設計のうち、乗員全員を生存させるのは 18 設計、そのうち `design_constraints.budgets` の内側に収まるのは **0** です。最軽量の生存設計は 4,000 kg の上限に対して 4,683 kg、500 MUSD に対して 696 MUSD です。どんな設計エージェントでも両立できません。本リポジトリが掲げる優先順位——ミッションが至上であり、設計要求はその下で改訂しうる——に従えば、動かすべき要求は予算のほうです。

### 簡潔な予測則

グリッドの半分で学習し、残り半分で評価した結果です。

| モデル | ホールドアウト R² | Balanced accuracy |
| --- | ---: | ---: |
| 定数 | −0.012 | 0.500 |
| ARS のみ | −1.384 | 0.627 |
| OGS のみ | 0.633 | 0.833 |
| カバレッジへの最小律 — `min(ρ_ARS, ρ_OGS)` | 0.396 | 0.881 |
| マージンへの最小律 — `min(ρ_i / ρ*_i)` | 0.886 | 0.902 |
| 直列（応答の積） | 0.902 | 0.912 |
| **応答への最小律 — 2 応答の `min`** | **0.936** | 0.902 |

**通常述べられる形の**最小律（リービッヒの法則）は成績が悪くなります。2 つのサブシステムが同じカバレッジで臨界になるわけではないからです（ρ*_ARS ≈ 0.17、ρ*_OGS ≈ 0.74）。素の最小値を取ると、数値的に小さいほうが閾値の低いほうと一致するセルでは律速サブシステムを取り違えます。**効くのは各サブシステムの自分の閾値に対するマージンであって、素のカバレッジではありません。**

### 可制御性は状態依存である

出荷時動作点では、ゲインが非ゼロなのは `plant_sim.ogs.max_o2_kg_day` だけです。action と policy のすべての軸はゲインが厳密にゼロで、20 倍の範囲で振っても生存乗員は変わりません。プラントは `min(リクエスト, 定格)` を供給し、出荷時リクエスト以上では 100 % の操作で `limited_by: ["ogs_capacity"]` を報告するためです。

酸素の枯渇を解消する（OGS = 42 kg/day）と、これらの軸のいくつかが生き返ります。

| 軸 | 部分空間 | 出荷時動作点のゲイン | O2 解消後のゲイン |
| --- | --- | ---: | ---: |
| `ars_action_co2_mass` | action | 0 | 1.076 |
| `ars_capacity_kg_day` | capacity | 0 | 1.076 |
| `o2_threshold_low` | policy | 0 | 1.076 |
| `co2_threshold_high` | policy | 0 | 0.538 |
| `ogs_max_o2_kg_day` | capacity | 1.165 | 1.165 |

出荷時設計器が好んで動かす軸は、一般に無意味なのではありません。**別のサブシステムを先に直すまで**無意味なのです。単一動作点で測った one-at-a-time 感度なら「この軸は死んでいる」と結論したはずで、2 本目のスイープこそが両者を区別します。

### 閉ループは飽和する

`labeled_rule_base` の 3 本のチェーンはすべて **saturating**（飽和）アーキタイプに分類されます。ループは着実に動き続けるのに、結果はまったく変わりません。

- ステップサイズは `0.386` 対数単位（= √3 · ln 1.25、3 本の action 軸に一定の +25 % ゲイン）で一定、減衰しません。
- 転回コサインは `+1.000` に張り付いています。完全な直進であり、探索ではありません。
- ステップの大きさの 100 % が `action` 部分空間に、`capacity` には 0 % が入ります。
- 提案の 40 % はシミュレーション前に破棄されます。チェーンは検証要求を凍結するためすべての `set_parameter` 変更を除去しますが、設計器には通知されないため、毎イテレーション同一の閾値変更を提案し続けます。

### 地形は単調ではない

ARS 軸に沿った容量増加のうち 16 % は結果を**悪化**させ、最悪の単一下降は生存率 0.24 に達します。ハードウェアを足すことが人命を奪いうるのは、操作が busy guard に対してスケジュールされるためです。バッチが大きいほどサブシステムを長く占有し、次の操作が必要だった窓を逃しかねません。ここでは単一評価による山登りは信頼できず、これはステップ幅を広げる根拠ではなく、tool-use 設計器の複数候補再シミュレーションを支持する根拠です。

## 軌跡アーキタイプ

チェーンは相互排他かつ網羅的な分類に、この順で判定されます。

| アーキタイプ | 意味 |
| --- | --- |
| `frozen` | 初回実行の後、設計変更が一切提案されない |
| `saturating` | ループは動き続けるが結果が変わらない |
| `converging` | 結果が改善し、ステップサイズが減衰する |
| `overshooting` | 少なくとも 1 回の方向反転を経て結果が改善する |
| `oscillating` | 持続的な改善なしに方向反転を繰り返す |

最初の分岐が重要です。何も提案しないループと、無効なものを提案するループは別種の失敗であり、対処は正反対です。

## モジュール構成

| モジュール | 責務 |
| --- | --- |
| `design_space` | カバレッジ比、アクチュエーションベクトル、フットプリント、予算、範囲 |
| `artifacts` | 実行／チェーンディレクトリをフラットな行として読む |
| `statistics` | ブートストラップ、並べ替え検定、Cliff's delta、ロジスティック当てはめ、Kaplan-Meier、log-rank、balanced accuracy |
| `loop_dynamics` | チェーンの順序変数、アーキタイプ、可制御性、実効ゲイン |
| `experiments` | `RunSpec`、CLI を駆動する実行器、spec ビルダー |
| `campaign` | 標準バッテリとそのグリッド |
| `figures` | インライン SVG として描画される matplotlib 図 |
| `report` | findings 辞書と HTML ドキュメント |

依存はプロジェクト既存のセット（numpy、matplotlib、PyYAML）の内側に留めてあり、シミュレータと同じ環境で解析が走ります。推定量は SciPy から持ってくるのではなく直接実装しており、いずれも読み切れる短さで、閉形式のケースに対してユニットテストされています。

レイヤ規則（`tools → scenario → environment → core`）は保たれています。本パッケージは scenario モジュールと実行成果物を読みますが、その逆はありません。

## 拡張する

**実験ブロックを追加する。** `experiments.py` に `list[RunSpec]` を返す spec ビルダーを書き、`campaign.build_specs` に登録し、その行を `CampaignResult` に加えます。

**アクチュエーション軸を追加する。** `design_space.ACTUATION_AXES` に、部分空間・設定ファイルの出所・ドット区切りパス・出荷時値を持つエントリを追加します。変位・ステップノルム・部分空間シェアは自動的に拾います。可制御性も測るなら `experiments.OAT_AXES` にも追加します。

**図を追加する。** `figures.py` にフラットな行を受け取り `to_svg` 経由で SVG 文字列を返す `fig_*` 関数を書き、`report.render` からキャプション付きで呼びます。

**LLM 設計器で回す。** プロバイダに到達できる環境なら、`chain_specs(..., design_mode="llm")` で `capacity_profile` 変更を発行できる tool-use 設計器を動かせます。可制御性と相図の結果はプラントの性質なのでどの設計器にも当てはまり、ループ力学の結果はチェーンを生成した設計器に固有です。

## 制約

- 出荷時バッテリでは両エージェント側とも `labeled_rule_base` です。ハードウェアをリサイズ**できる** tool-use 設計器は、LLM プロバイダなしでは動かせません。
- 全実行が `plant_sim` です。`mock` は生存・スコアカードのデータを出さず、`ros2` には SSOS Docker が必要です。
- スイープでは障害注入をオフにし、カバレッジだけが変わるようにしています。チェーンは出荷時デフォルト（有効）のままです。
- グリッドは WRS を固定しています。実測ゲインがゼロで、ベースラインのカバレッジが 6.4 であることが根拠です。

数値つきのレポート本体は `src/experiments/analysis/design_loop_analysis.html`（英語）と `design_loop_analysis.ja.html`（日本語）です。このページはそれを再生成するための運用ガイドです。
