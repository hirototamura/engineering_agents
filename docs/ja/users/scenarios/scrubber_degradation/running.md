# スクラバーの回復モードを比較する

[基本環境](../../quickstart.md)と、各実行の新しい保存先を準備します。エージェントなしとラベル付きルールにはモデルサービスは不要です。

```bash
PYTHONPATH=src python -m tools.cli run scrubber_degradation \
  --agents-mode none --steps 50 --run-id scrubber-baseline-01 --dry-run --json
PYTHONPATH=src python -m tools.cli run scrubber_degradation \
  --agents-mode labeled_rule_base --steps 50 --run-id scrubber-rules-01 --dry-run --json
```

計画を確認し、`--dry-run --json` を外して実行します。出力は `experiments/eclss/results/` に保存します。モード比較では異常、モデル係数、観測期間を揃えます。LLM を評価する場合は接続可能なサービスを設定し、新しい実行 ID で `--agents-mode llm` を使います。

両方の summary で最大 CO₂、最小・最終電力余裕、最初の閾値超過、回復ステップを比較します。テレメトリと回復コマンドのイベントから、どの操作が変化に先行したかを確認します。[結果契約](results.md)に境界と行の解釈があります。

エージェントありの実行は `design_proposals.json` も出力します。レビュー対象の推奨として扱ってください。このシナリオには、それを消費して恒久変更を再シミュレーションする対応コマンドはありません。ビューアの設計プレビューを改善の証拠にしないでください。

完了とは、両実行の設定と観測が保持され、回復の説明を操作とテレメトリへたどれることです。この簡易モデルで実物のスクラバーを妥当性評価したという意味ではありません。

## 実行を時系列で読む

| 段階 | エージェントなし | ラベル付きルール | LLM |
| --- | --- | --- | --- |
| 設定した異常の前 | 支援なしの軌跡を得る | 同じプラントを観測 | 同じプラントを観測 |
| 異常の開始 | 劣化が始まる | 記録した観測から診断 | モデルに依存する診断・議論 |
| 回復の機会 | コマンドなし | 方針で選ぶ操作 | モデルが選ぶ許可済み操作 |
| 観測終了後 | ベースラインの summary | summary とルール推奨 | summary と生成推奨 |

異常の開始ステップは[設定](configuration.md)で定義します。実際の閾値超過・回復時刻は各 summary から読みます。旧解説の概算時刻は受入基準ではありません。同じシミュレーションステップに揃え、受理した操作を比較してからチームと軌跡の差を結び付けます。
