# 成果物リファレンス

出力ディレクトリが証拠の単位です。リポジトリと外部入力のリビジョンとともに保持します。ファイルがあるだけでは成功や妥当性を示しません。

## 主な記録の役割

- `summary.json`: 完了した実行の条件、測定、状態、パスの概要。スキーマはシナリオごとに異なる。
- 保存設定または SSOT 入力: 適用変更を含め、実際に使った入力。
- `telemetry.jsonl` とイベント記録: シナリオの単位・時刻規則に沿った観測と操作。
- `design_proposals.json`: designer が動いた場合の、次に向けた変更案。スキーマと適用規則はシナリオが定める。
- 評価・レポート: 決定論的な確認と人が読むための派生表示。合計点より先に適用範囲と妥当性を見る。

ストリームは使用時に作られるため、すべての実行にすべてのファイルがあるとは限りません。提案は空や欠損の場合があり、評価は適用対象外や不完全の場合があります。3 シナリオ共通の単一合否スキーマはありません。

## 所有する契約へ進む

[スクラバー結果](../scenarios/scrubber_degradation/results.md)はテレメトリ、回復指標、messages、推奨の限界を定義します。[ECLSS 結果](../scenarios/ssos_eclss_loop/results.md)は正規の観測行、評価スキーマ、物理・整合性ゲート、消費済み提案、連鎖の証拠を定義します。[キューブ結果](../scenarios/balancing_cube/results.md)は変更しない設計・スクリーニング・独立検証・提案・同期の記録を定義します。

ECLSS 連鎖には `chain_summary.json`、`chain_final_answer.json`、番号付き実行ディレクトリ、任意の対比較リプレイが加わります。これは単一実行の summary とは異なります。`job run` の入力は実行仕様であり、検証レポートではありません。

[レポートライブラリ](../guides/reports.md)は HTML を索引化し、翻訳表示やサムネイルも生成できます。閲覧用の派生ファイルを使いつつ、引用する証拠は元の数値と条件の記録で確認してください。

保存・ストレージ内部・同期処理を変更する場合は[開発者向けストレージリファレンス](../../developers/reference/storage.md)を参照してください。

## 記録ごとに言えること

| 記録の種類 | 裏付けること | 単独では示さないこと |
| --- | --- | --- |
| 設定・凍結スナップショット | 入力の識別と宣言条件 | 正しい実行 |
| テレメトリ・ケース記録 | 観測したモデル挙動 | 要求合格 |
| イベント・コマンド結果 | 試行・受理・拒否した操作 | 後の変更が改善を生んだ因果 |
| 決定論的評価 | 宣言した評価器での結果 | 物理的忠実度 |
| 議論・仮説 | 提案者が実験を選んだ理由 | 想定メカニズムが真であること |
| 提案・選択 | 次の設計と選択理由 | 全提案フィールドの再測定 |
| 来歴・配送記録 | 追跡可能性と公開状態 | 工学的受入 |

比較には入力と評価の両方を残します。点数や画像だけでは、解釈に必要な条件が抜け落ちます。
