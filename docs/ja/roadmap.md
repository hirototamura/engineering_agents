# ロードマップ

ここに並んでいるのは願望ではない。すべて [50周の連鎖3本](results.md) が「足りない」と実測した項目であり、それぞれ着地するファイル名まで書いてある。

SSOS / ROS 2 統合のフェーズについては [SSOS ロードマップ](ssos/roadmap.md) を見る。

## P0 — 効くと実測されたものを固定する

chain memory は致命的な巻き戻り12回のうち11回を消した。この結果は今や**回帰リスク**である。メモが設計者に届かなくなっても、テストは1つも落ちない。

| やること | 場所 | 受け入れ条件 |
| --- | --- | --- |
| 2周目以降 `chain_memory_compact` が tool-use context に入ることを検証 | `tests/scenario/test_ssos_chain_memory.py` | メモを抜いた連鎖が失敗する |
| 記録された最良設計が ARS **と** OGS **と** WRS を含むことを検証 | `chain_memory.py` の `best_full_survival` | 2項目だけの best は拒否される |
| 部分提案が省いたフィールドをベースラインに戻さないことを検証 | `design_proposals.py` | 現状は**設計上落ちる** → P1 参照 |
| 観測した失敗境界を bad pattern として残す | `chain_memory.py` の `known_bad_patterns` | WRS=1.25 → 45/50 が次周のメモに残る |

## P1 — chain memory を「見せる」から「適用する」へ

最大の既知のギャップであり、コード自身のドックストリングがそう書いている。chain memory は次の周に何が効いたかを伝えるが、部分提案は今も省いたフィールドを落とす。見せるだけで実測上は足りた（巻き戻り12回→1回）が、機構としては注意書きであって修正ではない。

**修正の中身:** `applied_proposals` を累積設計状態としてマージし、名指しされなかったフィールドがシナリオ既定値へ落ちるのではなく**設置済みの値を保つ**ようにする。これは「設計者に何を伝えるか」ではなく「提案をどう運ぶか」の変更（`design_proposals.py`）である。

**なぜ先にやらなかったか:** アーカイブ内のすべての提案の意味が変わるうえ、安いほうの介入を単独で測る価値があったから。実際にあった。だから今度は高いほうをやる価値がある。

## P1 — 1軸より多く探索する

段階③の停滞検知は発火して探索を要求しているのに、返ってくる探索は依然として WRS のみである。ARS と OGS は理論下限に達して以降動いていない。

| 方向 | 根拠 |
| --- | --- |
| ARS ≥ 20.8、OGS ≥ 42.0 を下限として保持 | 下回ると乗員が死ぬ。好みではなく物理 |
| WRS 1.8–2.2 を重点探索 | 観測された有望帯 |
| WRS ≒ 1.25 を避ける | 実測された失敗境界（45/50） |
| WRS だけで改善しなくなったら ARS/OGS を 1–3 % 振る | 一度も試していない唯一の軸の組 |
| ARS/OGS を**下げる**探索は優先度を下げる | 乗員を失う事前確率が高い |

着地先は `chain_memory.py` の `_exploration_directive`。次周が読む文面はそこで組み立てている。

## P1 — 「採点が変わった」と「設計が良くなった」を分離する

段階③は 84 点、段階②は 66 点。その差のほとんどは採点関数であって機体ではない。この取り違えが二度と起こらないようにする。今後の比較は5列を必ず並べて出す。

```
新スコア | 旧スコアで再計算 | 総 M$ | 総 kg | 生存者数
```

着地先は `evaluation.py` と `tools/cli/output.py` の連鎖レポート。

## P2 — 探索中の安全下限

34周目は WRS を 1.25 まで下げて5人の命を使った。何も止めなかったし、現行方針では止めるべきでもない——探索は意図的に無制限で、**最終回答だけ**が全員生存を要求される。ただし「連鎖が既に生存可能な設計を持っているとき、緩い下限を置くべきか」は本物の未決の問いであって見落としではない。選択が選択のままであるようにここに記録する。

## P2 — 設計者向け context をさらに削る

体積はスコアに入っていない。`over_budget` は費用・質量が既に言っていることと重複する。両方ともログには残し、判断ページからは落とす。段階③で一部実施済み。`design_state.py` で仕上げる。

## P2 — 候補 ID と適用周を並べて表示する

連鎖の最高周と最終周はずれうる（段階③: 41周で 84.23、50周で 84.08）。差は小さいが、連鎖の出力が曖昧になる。選定候補 ID と、それが適用された周の両方を出す（`chain_selection.py`, `output.py`）。

## 現行ループの先

さらに先の話で、正直に言って投機的である。「先に何が真でなければならないか」と併記する。

**設計者を複数にする。** 現在の設計側は意図的に1人である（`agents.yaml`「**1体の**エージェントが自分で証拠を集めて設計に到達できるかが問い」）。提案者・懐疑者・費用責任者からなるレビュー委員会は次の自明な問いであり、そのための顔ぶれ機構は既にある（tool-use でない旧設計者は今も4人で討議する）。ただし単独エージェントのベースラインが固まっていないと、複数エージェントの結果を帰属できない。

**LLM 乗員の下の LLM 設計者。** 今日でも対応しているがほとんど走らせていない。非決定論の乗員は、設計の効果と「違う乗員が違う即興をした効果」を混同させるからである。`candidate_actor_mode` は「ベースラインは高価な乗員、候補は安い乗員」のためにある。足りないのはコードではなく実験計画である。

**ECLSS 以外のサブシステム。** EPS（電力）の ROS 2 ブリッジは既にある（`environment/ssos/eps/`）。電力予算の下で ECLSS を設計するのは、実質的にもっと難しく、もっと現実的な問題である。2つのサブシステムが同じ質量と同じワットを取り合うからである。

**能力以外の設計変数。** 冗長数、機器配置、運用方針。それぞれ採点する前に寸法モデルが要る。そこが本当の作業であり、`rack_affine_linear_v1` が算術1段落しかないことが、変数を3つに絞ってある正直な理由である。

**宇宙居住区の外へ。** このループ——精密な世界ルール、生データのみのエージェント入力、決定論の採点表、次周の制約として戻る設計提案——は ECLSS 固有ではない。実在の費用関数を持つ有限資源系ならどれでも当てはまる。電力上限のあるデータセンター、工場ライン、サプライチェーン。移植できるのは機構である。ただで移植できないのは物理モデルであり、それが無ければ全体はただのチャットログになる。
