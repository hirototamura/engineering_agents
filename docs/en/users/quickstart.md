# Complete a local design handoff

This tutorial uses `ssos_eclss_loop` with the local `mock` backend and labeled rules for both operations and post-run design. It needs Python 3.11 or newer and the repository checkout. No model service, Docker, or ROS2 is needed. The mock proves the proposal handoff; it does not verify plant capacity or physical safety.

## Prepare the checkout

From the repository root:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
PYTHONPATH=src python -m tools.cli scenarios
```

The list contains `scrubber_degradation`, `ssos_eclss_loop`, and `balancing_cube`. Optional requirements differ by [scenario](scenarios/index.md).

## Run once and retain the proposal

Use a fresh run ID. Existing ECLSS run directories are recreated by default; the [output rules](reference/configuration.md#output-directories) explain this behavior.

```bash
PYTHONPATH=src python -m tools.cli run ssos_eclss_loop \
  --backend mock --actor-mode labeled_rule_base \
  --design-mode labeled_rule_base --steps 20 \
  --run-id quickstart-run1 --set iteration.enabled=false --dry-run --json
```

Check that the plan names `mock`, both labeled modes, and `iteration.enabled: false`. Remove `--dry-run --json` to execute the same command. Explicitly disabling iteration selects one simulation instead of the configured chain.

The output is `experiments/eclss/results/quickstart-run1/`. Inspect `summary.json`, `telemetry.jsonl`, and `design_proposals.json`. The proposal should have `design_domain: ssos_graph` and nonempty `changes`.

## Review and apply the proposal

Open `design_proposals.json` and review `changes`, `final_status`, and `final_ineligible_reasons`. The mock has no plant verification, so its rule-generated proposal requires supervisor approval. For this local handoff demonstration, the following command explicitly accepts that unevaluated proposal. It does not approve a safe physical design.

```bash
PYTHONPATH=src python -m tools.cli run ssos_eclss_loop \
  --backend mock --actor-mode labeled_rule_base \
  --design-mode labeled_rule_base --steps 5 \
  --run-id quickstart-run2 --set iteration.enabled=false \
  --approve-provisional \
  --apply-proposals experiments/eclss/results/quickstart-run1/design_proposals.json
PYTHONPATH=src python -m tools.cli results quickstart-run2
```

The approval flag bypasses the proposal status gate for this manual application. It does not guarantee constraint compliance; the general [iteration guide](guides/design-iterations.md) explains the wider implications.

Completion means Run 1 remains intact, Run 2 contains `consumed_proposals.json`, and its saved configuration reflects the applied changes. Compare telemetry only over comparable conditions: the short second run establishes application, not a controlled improvement claim. Next use [ECLSS running](scenarios/ssos_eclss_loop/running.md) for a plant-based comparison and [inspect results](guides/inspect-results.md) to judge its evidence.

## Check the handoff on disk

After both commands finish, the important distinction is between a proposal *produced* by one run and the input *consumed* by the next:

```text
experiments/eclss/results/
├── quickstart-run1/
│   ├── scenario_config.yaml
│   ├── summary.json
│   ├── telemetry.jsonl
│   └── design_proposals.json       → proposed next change
└── quickstart-run2/
    ├── scenario_config.yaml        → effective applied configuration
    ├── consumed_proposals.json     → preserved handoff input
    ├── summary.json
    └── telemetry.jsonl             → new observations
```

Other evaluation and agent records may also be present. In Run 2, compare `consumed_proposals.json` with Run 1's proposal before reading any new proposal generated by Run 2. That new proposal concerns a later run.
